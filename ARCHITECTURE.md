# Curriculum: authored context registry and in-memory composition

Curriculum owns one registry over psyche-belief, mind-belief and field-belief roots refreshed from each repository's current origin/main before every Nexus start. Each root carries modules.datom, a vector of declarations `{ Kind subject Single.version «file» }` or `{ Kind subject Span.{ first last } «file» }`. A declaration gives one actual identity, `kind:subject:version` or `kind:subject:first-last`, to one source file whose basename is exactly `version.md` or `first-last.md`; no other declaration shares that file. Versions are nonnegative and a span is inclusive with its first bound below its last. The containing folders do not name a module, and a file no declaration names is not a module. A numeric request or dependency is a binding that selects every actual identity of its kind and subject containing the number, with the singleton first when present; an explicit span binding selects only that exact span. Selected actual modules are deduplicated while preserving deterministic binding order and retain their actual identities in text and provenance. Distinct intersecting spans coexist. A duplicate actual identity, a malformed span, an inadmissible span file, a mismatched source filename, a shared source file, an unreadable module body, a missing binding, a dependency cycle, overlapping roots or an unreadable modules.datom refuses admission. Recoverable singleton file-placement and name findings remain declaration reports. There is no implicit version, latest selection, legacy fallback or caller path registry.

The declared environment names are CURRICULUM_CONTEXT_LAYOUT=2 and the three repository directories and origin URLs. CriomOS-home fetches each origin/main before starting curriculum-nexus; Curriculum reads the checked-out commit from each Git root for provenance, then rechecks source bytes and canonical addresses before composition. A failed fetch or non-main checkout prevents the service from starting.

The socket is $XDG_RUNTIME_DIR/curriculum/curriculum.sock. The big-endian length-prefixed rkyv transport carries the Input and Output of signal-curriculum-nexus, the wire contract Flow and curriculum-deploy also depend on; the Nexus answers an Input with `input.answer(&curriculum)`, through the contract's generated Answering, one capability per input. Curriculum's own file formats (module declarations, roles, the workspace projection) are curriculum.ethos, over the contract's types, its Memory, the roles declared when it opened, is memory.ethos; nothing is stored. Its one external call, the refresh program (CURRICULUM_CONTEXT_REFRESH_PROGRAM) that brings the three checkouts to their origin mains before the registry is read, is emission.ethos: the registry emits RefreshContexts through ProcessLauncher, which runs the program as a child process, and acts on its RefreshOutcome, Refreshed, Failed or Unstarted. src/generated.rs, src/memory.rs and src/emission.rs are their generation, made by ethos-zero (the revision Cargo.toml names as the build-dependency) with `ethos-zero 'Generate.{ <repo>/curriculum.ethos <repo>/out }'` and committed; build.rs generates all three again at every build and fails when a committed file differs. The Datom CLI reads the contract's Input whole: ResolveSkills, ResolveSources, ComposeStartup and ComposeRole only. The former edit/rebuild/check/file-projection protocol is removed. Restart with the new immutable cohort to update registry contents; a changed source under an admitted registry refuses rather than silently changing a prompt.

ComposeStartup accepts a metaflow address, an explicit target harness and SYSTEM/USER module-ID vectors. It expands dependencies through this registry, deduplicates them, rejects contradictory or ambiguous placement and composes both texts in memory. Spirit and intent must be SYSTEM, and a startup requires both categories. This checks category placement, not an independent proof that the supplied intent is appropriate to a particular seat; Flow and its declared selection own that association. Source placement is explicit metadata, never inferred from model or title. An undeclared dependency reached from both placements refuses.

Target conditionals and raw blocks use the existing renderer syntax. Malformed or unknown directives and unresolved {{variables}} refuse. A variable placeholder is a matched `{{` and `}}` enclosing an ASCII identifier (`[A-Za-z_][A-Za-z0-9_]*`) with optional surrounding whitespace; other brace text, including fenced JSON and incomplete delimiters, is literal; shell ${...} examples remain literal. No caller inline-variable map exists. SourceSha256 covers complete authored bytes, BodySha256 covers the original instruction slice, RenderedSha256 covers target-rendered instruction bytes, and each complete output text has its own SHA-256. No composed prompt, skill, manifest or subagent file is written by the service.

Role metadata is server-declared CURRICULUM_ROLES_FILE: Roles contains explicit RoleDefinition records with name, surface, model, effort, permission, description module ID, exact belief module IDs, tools and caller policy. No prompt body or prose description is stored in that declaration. ComposeRole selects only by role name and surface and resolves every text from the same registry. It does not expand dependencies, standing context or workspace files. The reply returns text, policy and hashes, not a native subagent file. Native caller authentication and tool-dispatch enforcement remain the consumer's responsibility; returned caller policy does not authenticate a request. Role data requires a package built with the existing datom feature.

The canonical environment, role metadata and frozen source revisions are deployment authority. A metaflow tuple in a query is context addressing, not authenticated caller identity. This source does not claim an adversarial authorization boundary beyond refusing external prompt sources.


## Panel proof of concept (branch only)

A Panel is declared in modules.datom like another kind and has no description. It is resolved through the same typed registry but omitted from skill names, descriptions, and projected skill files. A master includes it with MiniJinja's default `{% include "panel:example:0" %}` syntax. MiniJinja's loader resolves only Panel identities, never filesystem paths or ordinary modules. Only target booleans are supplied as template context; unresolved variables refuse.

A system prompt, a startup prompt, and a role-context prompt each own an included-identity set. Each projected skill owns a fresh set. A panel is merged at the first rendered mark for its actual identity, including through nested panels; repeated or cyclic marks contribute no second copy. Missing panel names contribute empty text and are returned as typed MissingPanels in startup, role, and projection results. A direct startup or role selection of a Panel refuses. Target rendering occurs once before skill frontmatter adaptation.

This is an unapproved branch experiment, not a release. The mark was checked against a current 132-module declared source snapshot: MiniJinja default syntax preserved every source byte. A branch-only panel-syntax-audit binary records individual source hashes and parse/change findings. Neither this snapshot nor the experiment establishes syntax compatibility with future authored code. Panel dependency policy, cycle diagnostics, and separate merged-panel provenance remain design questions. Current per-parent RenderedSha256 covers merged text; original source/body hashes remain hashes of the master.
