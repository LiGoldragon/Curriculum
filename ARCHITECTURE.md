# Curriculum: authored context registry and in-memory composition

Curriculum owns one registry over psyche-belief, mind-belief and field-belief roots refreshed from each repository's current origin/main before every Nexus start. Each root carries modules.datom, a vector of declarations `{ Kind subject [ versions ] «file» }`, and a module's name comes from its declaration alone: kind:subject:version, once for each version the declaration holds for, its text in the declared file relative to the root. A file's own name and folder mean nothing, and a file no declaration names is not a module. The version is a canonical nonnegative decimal number, with zero written 0 and no leading zeroes. Every request and dependency names that version; there is no implicit version or latest selection. Supported kinds are spirit, intent, vision, knowledge, inquiry, compensation, role and raw. A name declared again, in the same root or a later one, is given by the first declaration; a declaration whose file is absent, is reached through a link or lies outside its root, whose name is invalid or which holds for no version is reported when the source is read and the rest admitted. A root without a readable modules.datom, overlapping roots, an unreadable module body, missing dependencies and cycles refuse admission. There is no legacy fallback or caller path registry.

The declared environment names are CURRICULUM_CONTEXT_LAYOUT=2 and the three repository directories and origin URLs. CriomOS-home fetches each origin/main before starting curriculum-nexus; Curriculum reads the checked-out commit from each Git root for provenance, then rechecks source bytes and canonical addresses before composition. A failed fetch or non-main checkout prevents the service from starting.

The socket is $XDG_RUNTIME_DIR/curriculum/curriculum.sock. The big-endian length-prefixed rkyv transport carries the Input and Output of signal-curriculum-nexus, the wire contract Flow and curriculum-deploy also depend on; the Nexus answers an Input with `input.answer(&curriculum)`, through the contract's generated Answering, one capability per input. Curriculum's own file formats (module declarations, roles, the workspace projection) are curriculum.ethos, over the contract's types, its Memory, the roles declared when it opened, is memory.ethos; nothing is stored. Its one external call, the refresh program (CURRICULUM_CONTEXT_REFRESH_PROGRAM) that brings the three checkouts to their origin mains before the registry is read, is emission.ethos: the registry emits RefreshContexts through ProcessLauncher, which runs the program as a child process, and acts on its RefreshOutcome, Refreshed, Failed or Unstarted. src/generated.rs, src/memory.rs and src/emission.rs are their generation, made by ethos-zero (the revision Cargo.toml names as the build-dependency) with `ethos-zero 'Generate.{ <repo>/curriculum.ethos <repo>/out }'` and committed; build.rs generates all three again at every build and fails when a committed file differs. The Datom CLI reads the contract's Input whole: ResolveSkills, ResolveSources, ComposeStartup and ComposeRole only. The former edit/rebuild/check/file-projection protocol is removed. Restart with the new immutable cohort to update registry contents; a changed source under an admitted registry refuses rather than silently changing a prompt.

ComposeStartup accepts a metaflow address, an explicit target harness and SYSTEM/USER module-ID vectors. It expands dependencies through this registry, deduplicates them, rejects contradictory or ambiguous placement and composes both texts in memory. Spirit and intent must be SYSTEM, and a startup requires both categories. This checks category placement, not an independent proof that the supplied intent is appropriate to a particular seat; Flow and its declared selection own that association. Source placement is explicit metadata, never inferred from model or title. An undeclared dependency reached from both placements refuses.

Target conditionals and raw blocks use the existing renderer syntax. Malformed or unknown directives and unresolved {{variables}} refuse; shell ${...} examples remain literal. No caller inline-variable map exists. SourceSha256 covers complete authored bytes, BodySha256 covers the original instruction slice, RenderedSha256 covers target-rendered instruction bytes, and each complete output text has its own SHA-256. No composed prompt, skill, manifest or subagent file is written by the service.

Role metadata is server-declared CURRICULUM_ROLES_FILE: Roles contains explicit RoleDefinition records with name, surface, model, effort, permission, description module ID, exact belief module IDs, tools and caller policy. No prompt body or prose description is stored in that declaration. ComposeRole selects only by role name and surface and resolves every text from the same registry. It does not expand dependencies, standing context or workspace files. The reply returns text, policy and hashes, not a native subagent file. Native caller authentication and tool-dispatch enforcement remain the consumer's responsibility; returned caller policy does not authenticate a request. Role data requires a package built with the existing datom feature.

The canonical environment, role metadata and frozen source revisions are deployment authority. A metaflow tuple in a query is context addressing, not authenticated caller identity. This source does not claim an adversarial authorization boundary beyond refusing external prompt sources.
